# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Static web explorer for NixOS, home-manager and nix-darwin module options, built to be **deployed in isolated environments**: no request may leave the site (vendored JS, bundled sources, no GitHub links), browsed as a tree of option paths (`nixos/{_module,appstream,boot,…}`), with fuzzy search and rendered Markdown docs. Built entirely with a Nix flake; no JS build step or npm (the build only minifies HTML/JS/CSS/SVG with `minify`, from nixpkgs). The only third-party JS is `marked`, vendored as one file, `site/marked.js` (v18.2.0 ESM build, unmodified).

## Commands

- `nix build .#site` — static site in `./result` (deployable as-is)
- `node --test tests/lib.test.mjs` — unit tests (also `nix build .#checks.<system>.lib`)
- `nix develop` — shell with node (for the unit tests)
- `nix run .#update-channels` — re-pin all channels from NixOS/infra `channels.nix` into `channels.json` (new releases are picked up automatically); `nix flake update` only updates build tooling

The flake only sees git-tracked files: `git add` (or `git add -N`) new files before `nix build`.

## Architecture

- **Data comes from upstream doc derivations, not from parsing Nix**, in `flake.nix` `channelOptions`. It uses non-flake entry points (stable across release branches), each on the channel's own nixpkgs:
  - NixOS: `nixos/lib/eval-config.nix { system = null; modules = [{ nixpkgs.hostPlatform = …; }]; }` → `.config.system.build.manual.optionsJSON` → `share/doc/nixos/options.json`
  - home-manager: `import <hm>/docs { pkgs; release; isReleaseBranch; }` (from `release.json`) → `.options.json` → `share/doc/home-manager/options.json`
  - nix-darwin: `import <darwin>/release.nix { nixpkgs; system; nix-darwin = { rev; shortRev; }; }` → `.docs.optionsJSON` → `share/doc/darwin/options.json`
- **Channels** come from `channels.json`, not from flake inputs: inputs can't be generated from data, so the only input is the nixpkgs used for tooling. `nix run .#update-channels` (the `update-channels` app inlined in `flake.nix`, run from the repo root) does the following:
  - reads https://github.com/NixOS/infra/blob/main/channels.nix and keeps `variant = "primary"` channels, including unmaintained ones; their `status` is shown in the UI.
  - maps each to its branches: nixpkgs `nixos-YY.MM`, home-manager `release-YY.MM`, nix-darwin `nix-darwin-YY.MM`, and `master` for unstable.
  - pins each branch with `git ls-remote` + `nix flake prefetch` (rev + narHash). It checks all three branches exist before prefetching, and reuses the narHash of a rev already in the lock, so only moved branches are downloaded.
  - skips a channel whose home-manager or nix-darwin branch doesn't exist yet, which happens right after a NixOS release.

  The flake fetches the pins with `builtins.fetchTree`, so eval stays pure. Lock order is UI order: unstable, then newest release first.

- **Site layout** (`result/`): `index.html`, `source.html`, `lib.js`, `nix.css`, `favicon.svg`, `marked.js`, `data/channels.json` (the repo's `channels.json` as-is, whose pinned revs are shown next to each source in the tree, plus per source `sizes` (data file bytes, for the loading percentage)), `data/<channel>/{nixos,home-manager,darwin}.json`, `src/<channel>/<repo>/<path>.nix`.
- **Bundled sources**: `channelSources` in `flake.nix` lists every declaring file plus their relative imports up to `IMPORT_DEPTH` (read from `lib.js`), using jq + grep so the build needs no node. Its jq copies of `normalizeDecl` and `nixImports` must stay in sync with `lib.js`; its grep also matches paths in comments and strings, which only bundles a few extra files. It then copies each one from the channel's nixpkgs/home-manager/nix-darwin input into `src/<channel>/`. That is about 3.2k files and 25 MB per channel. Missing declaring files are warnings, not errors: watch the build log.
- **Declaration jump**: options JSON has no line numbers, so `findOptionLines` searches for `<loc suffix> = mk*Option` and returns the range up to the closing `;` (found with the tokenizer). When several declarations match (`enable` for both `foo` and `foo.bar`), it keeps the one whose enclosing attribute names end with the most remaining segments; a tie returns no match. If the declaring file has no match, `source.html` searches its imports breadth-first, up to the depth the build bundles, and says "imported from …". Submodule options are usually declared in an imported file (e.g. nginx `vhost-options.nix`), and the options JSON names the importing file. With no confident match the page opens at the top, on purpose, because a wrong jump misleads.
- **Tree** = `<source>` then the option's `loc` segments. A node can be an option _and_ have children (e.g. submodule options). NixOS documents modular services as fake top-level options `<imports = [ pkgs.x.services.y ]>` (`nixos/modules/misc/documentation/modular-services.nix`). `buildTree` rewrites their `loc` to `["<modular services>", "pkgs.x.services.y", …]` and sets `option.modular`, which the UI uses for a `system.services.<name> = { imports = …; }` usage snippet. `option.name` stays the original, for `{option}` links. The UI sorts `<…>` names last. Names are coloured by depth (`.c0`–`.c5`, source = depth 0), the same in tree labels, indent guides and breadcrumb titles. In the UI, a chain of groups ending in a single option renders as one leaf (`appstream.enable`); every merged node maps to that leaf in `els`, so routes to any of them still resolve.
- **Declaration formats differ**; `normalizeDecl` turns them all into `<repo>/<path>` (repo: `nixpkgs`, `home-manager`, `nix-darwin`). NixOS gives repo-relative strings (`nixos/modules/…`), so they get a `nixpkgs/` prefix. HM and darwin give `{ name: "<home-manager/…>" }`. home-manager 26.05 also has absolute `/nix/store/…-source/…` strings, assumed to be nixpkgs. Directory declarations map to `default.nix`.
- **Markdown** is the nixpkgs dialect. `preprocessMd` turns `{option}` roles into in-page links, other `{role}` roles into code, and `::: {.note}` blocks into blockquotes before `marked` renders it. Descriptions contain raw `<…>` text, so the `marked` renderer escapes HTML and drops non-http(s) links. Keep that, because rendered output goes into `innerHTML`.
- **URLs**, readable on purpose:
  - Explorer: `?<channel>#<source>:<dotted name>`, e.g. `?nixos-26.05#nixos:services.nginx.virtualHosts.<name>.forceSSL`, for groups too. `optionName`/`optionPath` convert between tree paths and names as Nix writes them: segments with `.` are quoted (`boot.kernel.sysctl."net.core.rmem_max"`) and `<…>` placeholders stay atomic. `route()` resolves in the hash's own source first (exact option name through `byKey`, then tree path), and only then tries other sources' exact names (`{option}` doc links naming an option in another source), so a group in one source never jumps to a same-named option elsewhere. `showPath()` is the single entry point: it opens ancestor `<details>`, selects the node and renders it, or says the path isn't in that channel. The channel is the whole query string, written with `replaceState`; a missing or unknown one falls back to the newest `stable` channel (else the first).
  - Source: `source.html?<channel>/<repo>/<path>#L12-L20`. Explorer links end in `#<source>:<option name>` instead; the page swaps that for the found line range with `replaceState`. Line-number clicks also use `replaceState`, so the history stays explorer → source and "← Explorer" can use `history.back()` when the referrer is the explorer. Otherwise it links to `./?<channel>#<option>`.
- **Syntax highlighting**: `nixTokens` in `lib.js` is a small scanner (no library) with a context stack, so `${…}` interpolations inside strings are tokenized as code. That matters because nixpkgs nests `''…${ f ''…'' }…''`. It's used for `literalExpression` defaults/examples, ` ```nix ` blocks in descriptions (marked `code` renderer; other languages stay plain), the modular-services usage snippet and `source.html`. `nixHTML` escapes every token before it goes into `innerHTML`. `source.html` splits tokens into lines after tokenizing, so multi-line strings keep their colour.
- `site/lib.js` is pure logic (tree, decls, markdown preprocessing, fuzzy scoring, Nix tokenizer), tested with node. `site/index.html` holds the DOM code inline. Tree nodes render lazily on first open (~33k options).
